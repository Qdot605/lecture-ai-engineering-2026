- 第1回（素のLLM）とエージェントの回答の違い：
    - 第１回の素のLLMは、モデルが持つ知識をもとに直接回答するのに対し、今回のエージェントは、必要な情報をツールで取得し、その結果をもとに回答する点が異なる。
    - 今回の「LoRAとQLoRAの違いは？」という質問では、用語集からそれぞれの定義を検索して、量子化の有無を中心に違いを説明できていた。また、関係する講義回（第２回）も示されていた。
    - 第１回の回答との直接比較は今回実施していないが、エージェントでは外部情報を参照することで回答のこおんきょを確認できる点が重要だと理解した。
- `--trace` で見えたツール呼び出し（ツール名と引数）：
    1. 「LoRAとQLoRAの違いは?」
        - search_glossary({'query': 'LoRA'})
        - search_glossary({'query': 'QLoRA'})

        2つの用語に対して、それぞれ個別に検索ツールが呼ばれ、用語集に登録された定義と講義回が取得されていた。
    2. 「第2回の内容から確認問題を1問出して」
        - make_quiz({'lecture': 2})

        追加したツールが選択され、第2回の用語からLoRAに関する確認問題が生成された。
- 1つの質問での LLM 呼び出し回数（`requests`）：
    | 質問 | requests | tool_calls |
    | --- | --- | --- |
    | LoRAとQLoRAの違い | 2 | 2 |
    | 第2回の確認問題 | 2 | 1 |

    - 質問①では、最初のLLM呼び出しでLoRAとQLoRAの2つの検索をまとめて要求し、それぞれの検索結果を受け取った後、2回目のLLM呼び出しで最終回答を生成した。
    - 質問②では、最初のLLM呼び出しで make_quiz を選択し、ツールから取得した確認問題を2回目のLLM呼び出しで回答として出力した。

    この結果から、LLMへの問い合わせ回数（requests）とツールの実行回数（tool_calls）は必ずしも一致せず、1回のLLM呼び出しで複数のツール実行を要求できることを理解した。

- 追加したツールと、docstring に書いた説明：
    - **追加ツール: make_quiz(lecture: int) -> str**

    指定された講義回の用語集から1つの用語を選択し、その意味を問う確認問題と答えを返すツールを追加した。

    docstringには、指定した回の用語から確認問題と答えを生成すること、および「第2回の確認問題を出して」のように復習用の問題を求められた際に使用することを説明した。

    実行結果では、LLMが質問の意図に対して `make_quiz` を選択し、適切な引数 `lecture=2` を渡していることを確認できた。

- 気づき・学び：

    また、LLMの呼び出し回数とツールの呼び出し回数は必ずしも一致せず、ツールの説明(docstring)やエージェントへの指示(INSTRUCTIONS)が、ツール選択や実行方法に影響することを学んだ。

    エージェントの動作を理解・評価するには、最終回答だけでなく、`--trace`によってツール選択・引数・実行結果を確認することが重要だと感じた。

## 宿題

- 取り組んだレベル：**実装**

    Human-in-the-Loopによる承認付き学習記録保存ツールの実装

- やったこと：

    学習内容をMarkdownファイルへ保存する `save_learning_log` ツールを追加した。

    - `app/tools.py` に学習テーマと内容を受け取り、`learning_log/agent_learning_log.md` へ追記する関数を実装した。
    - `app/agent.py` で `requires_approval=True` を指定し、保存前にユーザーの承認を必須とした。
    - `DeferredToolRequests` によってツールの実行を一時停止し、CLIで承認・拒否を選択できるようにした。
    - 承認結果を `DeferredToolResults` として渡し、エージェントの処理を再開する仕組みを実装した。
    - GitHub Copilotを活用して実装し、pytestによる動作検証を行った。

- 結果：
    - **自動テスト**

    uv run pytest -q の結果、55件のテストが成功した。

    - **承認時（y）**

    `save_learning_log` が呼び出され、保存予定のテーマと内容が表示された。`y` を入力すると、学習内容がMarkdownファイルに追記されたことを確認した。

    - **ツール呼び出し**

    save_learning_log({'topic': 'LoRAとQLoRAの違い', 'content': 'LoRAは低ランク行列によって学習パラメータを削減する手法、QLoRAはさらにベースモデルを量子化してメモリ使用量を削減する手法であることを学習した。'})

    - **ツール実行結果**

    学習記録を learning_log/agent_learning_log.md に追記。

    - **拒否時（N）**

    同じ質問を実行し、承認画面で N を入力したところ、ツールは拒否され、ログに以下が出力された。

    The tool call was denied.

    その後のファイル内容にも、拒否した学習記録の追記は確認されなかった。

- 気づき・疑問：

    今回の実装を通じて、LLMはツールの選択と引数の決定を行い、実際のツール実行はプログラム側が制御していることを理解した。

    特に、`requires_approval=True` を設定することで、LLMが保存を要求してもユーザーの承認がなければ実行されないことを確認できた。このことから、LLMへの指示だけに頼らず、プログラム側で実行を制御することの重要性を学んだ。

    また、保存を拒否した際、実際には保存されなかったものの、LLMは再び承認を求める回答を生成した。この結果から、ツールの実行制御が正しく機能することと、LLMの回答が適切であることは別の評価観点であると気づいた。
